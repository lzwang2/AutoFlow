## 1. 目的

本文档定义 AutoFlow 中“脚本复用模型”的整体设计，包括：

- 线性脚本与规则循环的职责边界
- 视觉判定条件的复用方式
- 动作与动作片段的复用方式
- 模板库分层原则
- 对当前工程的落地约束

其核心目标是：在保留两种脚本执行模型差异的前提下，统一底层复用对象，并避免在 UI/语义层把两种脚本语义混淆。

---

## 2. 背景与问题描述

当前系统同时存在两种脚本表达方式：

- 线性脚本：按顺序执行，一条接一条，适合固定流程
- 规则循环：持续监控当前画面，按条件判断命中规则，然后执行动作，适合游戏状态驱动场景

这两种脚本模型共享大量底层能力：

- 点击
- 等待
- 图像识别
- 区域裁剪
- 颜色判断
- 状态判断
- 调用技能

但它们的执行语义并不相同，因此不能简单地把它们看成同一种脚本语言。

关键问题在于：

- 线性脚本和规则循环都依赖视觉判定
- 视觉判定条件本身是高度可复用的
- 动作序列也高度可复用
- 复用发生在“动作层”和“判断层”，而不是“脚本执行模型层”

因此，系统需要一个统一的复用模型，而不是单纯地把两套编辑器合并成一个。

---

## 3. 设计目标

### 3.1 目标

1. 把“动作复用”和“视觉判定条件复用”统一纳入同一套设计
2. 让线性脚本和规则循环共享公共能力，而不混淆运行语义
3. 支持以下复用形态：
   - 原子动作复用
   - 连续动作片段复用
   - 图像判定条件复用
   - 规则模板复用
4. 保持编辑器直观，避免把规则脚本和流程脚本塞进同一套 DSL

### 3.2 非目标

- 不把规则循环完全降级为线性脚本
- 不把线性脚本完全上升为规则脚本
- 不让视觉判定和动作步骤混成同一个对象语义

### 3.3 本轮明确不做

以下内容属于后续独立议题，本轮设计和实现都不涉及：

- **技能层整合**：`AutoFlow.Core/Skills/` 下的硬编码技能（`LastCloudiaCommon` 等）目前独立维护自己的图片和区域坐标，与规则模板存在重复。这是 [Skills_Architecture_Decision.md](../../architecture/Skills_Architecture_Decision.md) 的既有决策结果，不在本轮范围内。因此 NFR-01「一张图只定义一次」**只约束脚本层（线性脚本 + 规则脚本 + 模板库）**，不约束技能层。技能层如何复用 `VisualConditionSpec` 留待后续评估。
- **编辑器拖放交互**：模板复用在本轮通过"选择/引用"完成（对话框或下拉选择），不引入拖放。
- **颜色条件、复合条件（AND/OR/NOT）**：仅保留扩展空间，不在本轮实现。

## 4. 设计原则

### 4.1 分离执行模型与复用模型

执行模型是脚本如何运行：

- 线性执行
- 持续循环判断
- 事件驱动分支

复用模型是脚本如何构造与复用：

- 原子动作
- 宏动作
- 图像条件
- 规则模板

这两个层次必须分离。

### 4.2 视觉判定是核心复用对象

在游戏自动化里，真正难复用且高频出现的，是“同一张图 + 同一块区域 + 同一套阈值”的判定逻辑。

例如：

- 无法加入弹窗
- 主页入口
- 战斗结束界面
- 准备按钮
- 网络错误提示

这些判定单元是所有脚本编辑器都应共享的。

### 4.3 动作也应设计为可复用对象

多个脚本场景常会重复同样的动作序列：

- 关闭弹窗并重试
- 打开背包并点击装备
- 等待主界面稳定后点击开始
- 退出战斗并回到主菜单

这些动作应先设计为可复用动作块，再在规则或线性脚本中使用。

### 4.4 共享资源，但不共享运行语义

系统可以共享：

- 图片资源
- 区域定义
- 阈值参数
- 点击坐标模型
- 调用技能参数结构

但不能共享：

- 规则的“触发条件”语义和线性脚本的“顺序执行”语义
- 规则循环的“每帧判定”与线性脚本的“单次按顺序推进”

## 5. 需求定义

### 5.1 功能需求

#### FR-01：统一视觉判定对象

系统必须提供共享的视觉判定对象，用于统一描述一项图像匹配判断。

该对象应支持：

- TemplatePath
- 目标区域定义
- 阈值参数
- 图像资源描述和分类信息

该对象**不包含超时**。超时属于调用方语义（线性脚本轮询等待需要，规则循环单帧判定不需要），必须留在调用点参数中，见 FR-09。

#### FR-02：线性脚本可复用视觉判定

线性脚本中的 WaitImage 必须能够引用共享视觉判定对象，而不是直接重复写死一份图片路径和区域值。

#### FR-03：规则脚本可复用视觉判定

规则循环中的 IfImage 必须能够引用同一视觉判定对象，而不是复制一份独立模板定义。

#### FR-04：动作可复用

系统必须支持将一串原子动作封装为 ActionBlock，并在脚本编辑器中复用。

#### FR-05：动作块可嵌入规则和线性脚本

ActionBlock 必须允许被：

- 线性脚本的步骤列表引用
- 规则动作列表引用

#### FR-06：模板库分层

系统必须按语义保持不同模板库：

- 视觉条件模板库
- 动作模板库
- 线性脚本模板库
- 规则模板库

#### FR-07：对象持久化支持

视觉判定对象、动作块、规则对象和线性脚本对象必须支持 JSON 序列化与反序列化。

#### FR-08：语义隔离

规则对象和线性脚本对象必须保留各自运行语义，不能在底层被强制合并成同一个执行类型。

#### FR-09：调用方参数与判定对象分离

判定对象只描述"如何判定"，调用方参数描述"如何使用这次判定"。

- 属于 `VisualConditionSpec`：TemplatePath、区域、MatchThreshold、MeanDiffThreshold
- 属于调用点（`ActionSpec.Parameters` / 规则字段）：WaitTimeoutMs、PollIntervalMs、ClickAfterMatch、期望结果取反

原因：同一个"网络错误弹窗"条件，在线性脚本里可能等 30 秒、在另一处等 3 秒、在规则循环里根本不等待。把超时放进条件对象会导致同一条件必须复制多份，正好违背 NFR-01。

#### FR-10：坐标参照空间显式化

`VisualConditionSpec` 的区域坐标是**绝对像素值**，只在特定参照分辨率下有意义。因此：

- `VisualConditionSpec` 必须记录自身的参照空间：`ReferenceOuterWidth` / `ReferenceOuterHeight`
- 脚本引用条件时，若脚本的 `OuterWidth` / `OuterHeight` 与条件声明的参照空间不一致，必须给出明确警告或拒绝加载，不允许静默按错误坐标匹配
- 本轮不做自动缩放。模板图片本身没有尺度不变性（OpenCV 模板匹配对缩放敏感），跨参照空间复用条件在技术上不成立，只能报错

这是复用引入的**新风险**：条件从"脚本内联"变成"跨脚本共享"后，原本由所属脚本隐式保证的参照空间不再成立。

#### FR-11：一次性迁移与旧格式移除

现有磁盘资产全部是内联条件格式（`RuleTemplates/LastCloudia/*.rules.json` 等，`FormatVersion = 1`，条件直接写在 `Rule.TemplatePath` / `MatchThreshold` / `RegionX1..Y2` 上）。

**本轮不做向后兼容。** 采取"新代码 + 一次性迁移 + 删除旧格式"的路线：

- 引入 `conditionRef` 的格式记为 `FormatVersion = 2`，是**唯一**受支持的格式
- 加载器遇到 `FormatVersion != 2` 必须**明确拒绝并报错**，错误信息指出文件路径、实际版本号和迁移方式。不允许静默按 v2 解析（否则 v1 文件的内联字段会被丢弃、区域坐标退化为默认值，是最危险的失败模式）
- 必须提供迁移工具，把内联条件提取为共享条件文件并改写脚本为引用式
- 迁移完成并验证通过后，删除 `Rule` 上的内联条件字段（`TemplatePath`、`RegionX1..Y2`、`MatchThreshold`、`MeanDiffThreshold`）及解释器中对应的求值分支，不保留双路径
- 内联条件与 `conditionRef` **不共存**

选择不兼容的依据：待迁移脚本共 13 份、全部在仓库内受版本控制、单人使用、无外部存量数据。兼容层的价值在于保护无法触及的用户数据，此处不存在这种数据；维持双路径的代价是 `Rule` 上永久保留一组废弃字段和一个走不到的解释器分支。

放弃兼容后，安全网由迁移验证承担，见 AC-06。

---

### 5.2 非功能需求

#### NFR-01：可维护性

同一张图和同一块区域只应定义一次，不能散落在多个脚本文件中。

#### NFR-02：可扩展性

新增动作类型或判定类型时，不应破坏现有脚本对象结构。

#### NFR-03：可验证性

每个对象都应可通过单元测试验证其序列化、反序列化和引用解析行为。

#### NFR-04：低耦合

执行层只依赖抽象对象，不直接耦合 UI 和模板文件格式。

## 6. 约束与不变性

### 6.1 运行语义约束

- 线性脚本继续保留顺序执行语义
- 规则循环继续保留每帧判断语义
- 两者共享底层对象，但不共享执行器语义

### 6.2 复用约束

- 同一图像判断必须唯一维护
- 同一动作片段必须可跨脚本类型复用
- 规则模板与线性脚本模板不应相互强耦合

### 6.3 资源约束

- 图片资源路径必须支持模板目录解析
- 图片资源引用应允许相对路径和全局模板路径解析
- 缺失图片时必须保留清晰错误信息

### 6.4 存储布局与路径解析

现状（[RuleScriptService.cs:26-70](../../../AutoFlow.Core/Scripting/Rules/RuleScriptService.cs#L26-L70)）：规则里的相对 `TemplatePath` 按两级回退解析——先相对**脚本文件所在目录**，再相对 `<AppBase>/RuleTemplates`。共享条件库必须沿用同一套解析策略，不另发明一套。

现有代码里存在两个名字相似但用途无关的"模板目录"，本轮必须先厘清，不要误当成同一个：

| 代码位置 | 默认值 | 实际用途 |
|---|---|---|
| `RuleTemplateService._templateDirectory` | `<AppBase>/RuleTemplates` | 规则模板库（`.rules.json`） |
| `MainViewModel.TemplateDirectory` | `<AppBase>/Templates` | 手工截图的保存输出目录（`.png`） |

另外 `我的文档/AutoFlow/` 目前**只存 `window-profiles.json`**（见 `WindowTargetProfileService`），不是模板目录，也没有用户可配置的模板库根——`RuleTemplateService` 全项目只在 `TemplateSelectionDialog` 里以无参构造使用，即始终取默认值。

现有结构是**按游戏分目录**的，且 `SelectedGame` 参与模板保存路径（`Path.Combine(GetTemplateDirectory(), SelectedGame, name + ".rules.json")`）。模板分层必须保留这一维度，不能拉平：

```
<TemplateRoot>/                    = <AppBase>/RuleTemplates
  <Game>/                          # 如 LastCloudia
    images/                        # 图片资源（位置不变）
    Rules/                         # 规则模板库     *.rules.json
    Conditions/                    # 视觉条件模板库 *.condition.json
    Actions/                       # 动作片段模板库 *.actionblock.json
    Scripts/                       # 线性脚本模板库 *.json
```

四类模板取**平级子目录**，包括把现有 11 份 `*.rules.json` 从 `<Game>/` 根下挪进 `Rules/`。

这一条在 v0.4 里的结论是相反的（只为新类型开子目录、不挪既有文件），理由是"挪动属于纯位置变更、没有功能收益，且要连带迁移用户本地已存的模板"。改为 FR-11 的一次性迁移路线后，这两条理由都不再成立：

- 迁移工具本来就要逐份重写全部 13 份文件（内联条件 → `conditionRef`），顺带改变输出路径是零边际成本
- 不存在"用户本地已存的模板"。`RuleTemplateService` 全项目只以无参构造使用，目录固定为 `<AppBase>/RuleTemplates`，位于构建输出内，每次构建重新生成

实际代价只剩两处代码改动：`MainViewModel` 的模板保存路径（`Path.Combine(GetTemplateDirectory(), SelectedGame, name + ".rules.json")`）和模板枚举逻辑，都需要补上 `Rules` 一层。`images/` 不动，因此已有 `TemplatePath` 字符串（如 `LastCloudia/images/unable_to_join.png`）无需改写。

相对 `TemplatePath` 的解析顺序，沿用现有两级回退：

1. 相对**引用它的文件**所在目录（脚本或条件文件与自带图片放在一起的情况）
2. 相对 `<TemplateRoot>`（共享模板图片的情况）

两级都找不到时报错，错误信息列出尝试过的完整路径——现有实现已经这么做，保持。

这里有一个**取舍**需要留意：第 1 级以引用者所在目录为基准，意味着条件文件被移动到别的目录后，靠第 1 级命中的相对路径会失效（第 2 级仍可兜住放在 `<TemplateRoot>` 下的共享图片）。

保留这个顺序而不是改成"一律以 `<TemplateRoot>` 为基准"，理由是：现有 11 份规则模板和用户脚本都依赖当前行为，改基准会静默改变已有脚本的解析结果，代价大于收益。**因此约定：进入条件库的共享条件，其 `TemplatePath` 一律写成 `<Game>/images/<文件名>` 形式（以 `<TemplateRoot>` 为基准）**，从而只依赖第 2 级回退，天然免受条件文件移动影响。第 1 级留给脚本自带的私有图片。

这也正是现有 11 份规则模板已经在用的写法（如 `LastCloudia/images/unable_to_join.png`），且 `images/` 在本轮不挪位置，因此共享条件迁移时 `TemplatePath` 可以原样搬运，无需改写。

反过来说，`.rules.json` 从 `<Game>/` 挪进 `<Game>/Rules/` 之所以安全，正是因为这 11 份的路径全部靠第 2 级（`<TemplateRoot>` 基准）命中，与引用者自身位置无关。

依赖第 1 级的情况确实存在：`TestScripts/MultiPlayerGame.rules.json` 引用 `images/welcome.png` 和 `images/no_room.png`，图片实际位于 `TestScripts/images/`，靠同目录回退解析。该脚本不属于模板库、迁移时原地不动，因此第 1 级仍然成立，无需改写。这说明第 1 级回退是有实际用途的（脚本自带私有图片），不应取消。

结论：迁移时凡是改变了脚本文件位置的，必须检查其 `TemplatePath` 是否依赖第 1 级；位置不变的不必动。具体清单见 [Script_Reuse_Plan.md](Script_Reuse_Plan.md) Phase 6「路径改写规则」。

绝对路径原样使用，但应在保存时警告——现有 `TestScripts/test.rules.json` 里就存在写死到 `bin/x64/Debug/` 的机器相关绝对路径，这类内容不可分享。

条件 ID：

- 全局唯一，建议 `<分类>.<名称>` 形式（如 `LastCloudia.NetworkError`）
- 解析失败必须报出"哪个脚本的哪条规则引用了哪个不存在的 ID"，不允许静默跳过

## 7. 设计建议与落地原则

### 7.1 先抽象对象，再接解释器

在实现时必须先确定模型对象，再改写脚本解释器和 UI 绑定逻辑。

原因：如果先改执行器，很容易把规则语义、线性语义和公共型对象混成不可维护状态。

### 7.2 统一对象，不统一执行模型

最关键的原则是：

- 共享的是“判定”和“动作”对象
- 不共享的是“脚本执行模型”

### 7.3 先做最小共用骨架

推荐优先落地对象：

- VisualConditionSpec
- ActionSpec
- ActionBlock
- Rule
- ScriptDocument

这一层是后续工程最重要的基线。

## 8. 总体架构

整个系统可以分成 4 层：

### 8.1 基础资源层

负责底层能力和共享资源：

- 图像模板
- 区域坐标
- 匹配阈值
- 输入模拟
- 窗口捕获
- 坐标转换
- 视觉匹配服务

这一层不带脚本语义。

### 8.2 语义对象层

这是复用核心层，定义可复用对象：

- 原子动作
- 动作片段
- 视觉判定条件
- 条件模板
- 宏动作对象
- 规则对象
- 线性脚本对象

这一层负责“是什么”，而不是“怎么运行”。

### 8.3 编辑器层

负责展示和编辑：

- 线性脚本编辑器
- 规则循环编辑器
- 动作模板库
- 视觉条件模板库
- 规则模板库

这一层是用户可视层，不直接决定运行时语义。

### 8.4 执行层

负责按脚本模型执行：

- 线性脚本解释器
- 规则循环解释器
- 事件/状态驱动调度器

这一层只负责“怎么跑”。

## 9. 关键抽象对象

### 9.1 原子动作

这是最底层的动作定义，适用于所有脚本模型，且不依赖视觉判定对象本身：

- Click
- WaitTime
- Loop
- CallSkill
- Comment

注意：

- WaitImage、WaitColor、IfImage 不是纯原子动作
- 它们本质上是“条件型动作/条件节点”，依赖共享的视觉判定对象
- 这些判定对象需要单独抽象为 VisualConditionSpec

特点：

- 语义明确
- 单一职责
- 可组合
- 可被动作模板复用

---

### 9.2 视觉判定条件

这是最重要的可复用对象之一。

它回答的问题是：“用某张图，在某个区域内，按照某种阈值策略，判定是否命中”。

字段定义见 [§11.1 视觉判定对象](#111-视觉判定对象)。此处只说明它的语义地位：

- 它有独立的稳定标识（`Id`），因为它要被跨脚本引用；引用指向 `Id` 而非名称
- 它**不含超时**，超时属于调用方，见 FR-09
- 它必须声明自己的坐标参照空间，见 FR-10

它与 WaitImage / IfImage 的关系是：

- WaitImage 和 IfImage 都只是“使用该条件”的调用方式
- 真正的复用对象是 VisualConditionSpec
- 不是动作名本身在复用，而是共享条件对象在复用

这个对象既可以用于：

- 线性脚本中的 WaitImage
- 规则模板中的 IfImage 条件
- 图像模板库中的判定模板

因此它应该是第一层真正的共同抽象。

---

### 9.3 动作片段 / 宏动作

动作片段定义一串顺序执行的动作，适合复用。

字段定义见 [§11.3 动作片段对象](#113-动作片段对象)。此处只说明它的语义地位：

- 它是**固定步骤序列**，本轮不参数化（不引入 `Parameters`、`Preview`）；参数化动作块留待后续，需要先有明确用例
- 它声明自己依赖哪些视觉条件，但只存条件 `Id`，不存条件副本

例如：

- CloseAndRetryFlow
- EnterMainMenuFlow
- WaitBattleReadyFlow

作用：

- 在线性脚本中复用
- 在规则动作列表中可插入
- 在模板库中保存

这就是“先在线性中设计通用动作，再让规则模板组合”的核心思路。

---

### 9.4 规则模板

规则模板的本质是：

- 条件：视觉判定条件
- 动作：动作列表或动作片段引用

即：

- Rule = Condition + ActionSequence

它不等同于线性脚本，也不应该用线性脚本语义来强行解释。

---

### 9.5 线性脚本模板

线性脚本模板是：

- 一组顺序执行的动作
- 或一段动作片段集合
- 可被另一个脚本引用

它的用途是：

- 固定流程复用
- 常用步骤块复用
- 作为规则动作列表的子结构

---

## 10. 统一复用模型

### 10.1 复用分类

#### A. 原子动作复用

适用范围：[§9.1](#91-原子动作) 列出的原子动作。依赖视觉判定对象的 `WaitImage` / `WaitColor` / `IfImage` 不在此列，归入下面的 B 类。

复用方式：

- 从动作库中选择并插入

#### B. 视觉判定复用

适用于：

- WaitImage
- IfImage
- 图像存在/不存在判定
- 区域判定对象

复用方式：

- 复用同一张图片
- 复用同一块区域
- 复用同一组阈值参数
- 复用同一个判定配置对象

这是最关键的共享对象。

#### C. 动作片段复用

适用于：

- 关闭弹窗 + 等待 + 重试
- 进入主界面 + 点击开始
- 考虑等待和重试逻辑的完整动作组合

复用方式：

- 将动作序列保存为模板
- 线性脚本和规则动作都可引用

## 11. 一个统一的数据模型

以下是一个适合工程落地的统一设计模型。

### 11.1 视觉判定对象

`VisualConditionSpec`

- Id
- Name
- Description
- TemplatePath
- RegionX1
- RegionY1
- RegionX2
- RegionY2
- MatchThreshold
- MeanDiffThreshold
- ReferenceOuterWidth
- ReferenceOuterHeight
- Tags
- Category

它表示：

“这个判定条件是什么，以及如何判断”。

字段约束：

- `RegionX1..Y2` 全为负值表示"整帧匹配"，与现有 `Rule.HasRegion` 语义一致
- `ReferenceOuterWidth/Height` 是这组区域坐标所属的参照空间（脚本的目标窗口外框尺寸），见 FR-10
- 不含超时，见 FR-09

---

### 11.2 原子动作对象

`ActionSpec`

- Id
- Name
- Type
- Parameters
- Notes
- Category

例如：

- Type = Click
- Parameters = { x, y, button, clickCount }

或：

- Type = WaitImage
- Parameters = { conditionId, timeoutMs }

#### 与现有 `Instruction` 的关系（重要）

现状：`AutoFlow.Core/Scripting/Instructions/Instruction.cs` 是一个**扁平强类型 DTO**——所有命令类型的字段摊平在同一个类里（`PositionX`、`TemplatePath`、`WaitTimeMilliseconds`、`SkillParameters`…），7 个 `IInstructionHandler` 直接读这些字段，`InstructionViewModel` 和 XAML 也全部绑定在上面。

**本轮决策：不改造 `Instruction`。**

- `Instruction` 继续作为**执行期模型**，保持扁平强类型，handler 层和 ViewModel 层不动
- `ActionSpec` 只作为**模板库的序列化形态**存在，用于动作模板和 `ActionBlock` 的持久化与跨脚本传递
- 两者之间提供双向映射：`ActionSpec.ToInstruction()` / `Instruction.ToActionSpec()`
- `ActionSpec.Type` 直接复用现有 `CommandType` 枚举，不新建枚举

理由：把 `Instruction` 换成 `Type + Dictionary<string, object>` 会连带重写 7 个 handler、`InstructionViewModel` 和大量 XAML 绑定，属于纯重构成本，对"复用"这个目标没有增益。映射层的成本是一个文件，可控。

由此产生的约束：`ActionSpec.Parameters` 的键名必须与 `Instruction` 的属性名一一对应，映射失败时报明确错误而不是静默丢字段。

---

### 11.3 动作片段对象

`ActionBlock`

- Id
- Name
- Description
- Steps: List<ActionSpec>
- ConditionRefs: List<string>
- Category

它是一个有序的动作集合，适合复用。

`ConditionRefs` 存的是**条件 ID 列表**，不是条件对象副本。存对象副本等于把复用退化成拷贝，违背 NFR-01。这个字段的作用是声明"本动作块依赖哪些条件"，便于导入动作块时一并校验条件是否存在。

---

### 11.4 规则对象

`Rule`

- Id
- Name
- Description
- Enabled
- ConditionRef: string（条件 ID）
- Actions: List<ActionSpec or ActionBlockRef>
- TriggerOnce

这个对象设计的关键点是：

- 规则条件不再直接写死为 TemplatePath 字符串
- 而是引用一个统一的视觉判定对象

这样，规则模板和线性脚本都可基于同一视觉判定对象复用。

#### 关于 Priority

**本轮不加 `Priority` 字段。**

现有语义是 `RuleLoopInterpreter.EvaluateRules` 从上到下扫描、首个命中即执行（见 [RuleLoopInterpreter.cs:111-142](../../../AutoFlow.Core/Scripting/Rules/RuleLoopInterpreter.cs#L111-L142)），即**优先级 = 列表顺序**，编辑器的上移/下移按钮就是优先级调整手段。

引入独立 `Priority` 数值会产生两套排序依据（列表顺序 vs 数值），必须再定义谁覆盖谁、相等时如何 tie-break、编辑器上移下移改哪一个——这些复杂度换来的收益仅仅是"不用拖动列表"。在本轮"统一复用对象"的目标下属于无关变更。

后续若确实需要（例如动态启停规则组），应作为独立议题设计，并明确它替代而非叠加列表顺序。

#### `ConditionRef` 的加载语义

按 FR-11，`Rule` 上**不再保留**内联条件字段（`TemplatePath` / `RegionX1..Y2` / `MatchThreshold` / `MeanDiffThreshold`），这些字段在迁移完成后从类定义中删除。加载语义只有两种：

1. `ConditionRef` 非空 → 解析共享条件；解析失败按 AC-08 报错，不允许静默跳过
2. `ConditionRef` 为空 → 无条件规则（现有 catch-all 语义，保持不变）

保留 catch-all 是因为 `RuleLoopInterpreter` 现有行为就是"空 `TemplatePath` 视为无条件命中"（见 [RuleLoopInterpreter.cs:111-142](../../../AutoFlow.Core/Scripting/Rules/RuleLoopInterpreter.cs#L111-L142)），且 `MultiPlayerGame.rules.json` 一类的兜底规则依赖它。这不是兼容旧格式，而是这条语义本身仍然有用。

`Rule` 类采取**原地修改**（保留类名，删旧字段加 `ConditionRef`），不新建并存的类型——既然不留兼容路径，就没有两套类型并存的必要，且可避免连带改动 `InstructionViewModel` 与 XAML 绑定。

---

### 11.5 线性脚本对象

`ScriptDocument`

- Id
- Name
- Steps: List<ActionSpec or ActionBlockRef>
- Metadata

采取**原地修改**现有 `AutoFlow.Core/Scripting/ScriptDocument.cs`，不新建类型：`Instructions` 保留（执行期仍用 `Instruction`，见 §11.2），新增 `Id` / `Name`，`Steps` 作为序列化形态由 `Instructions` 映射得到。`OuterWidth` / `OuterHeight` 保留不动——它们是 FR-10 参照空间校验的比较基准。

与 `Rule` 同理（§11.4）：既然不保留兼容路径，就没有两套类型并存的必要。

如果需要更强复用，步骤也可以允许：

- 原子动作
- 动作块引用
- 条件引用

---

## 12. 运行时解释

### 12.1 线性脚本运行

线性脚本解释器按顺序执行：

1. 读取下一步动作
2. 若动作是原子动作，直接执行
3. 若动作是动作块引用，展开为步骤列表后执行
4. 若动作依赖视觉判定对象，则调用 VisualConditionSpec 检查

---

### 12.2 规则循环运行

规则循环每一帧都做：

1. 获取当前截图
2. 逐条评估规则条件
3. 规则条件本质是 VisualConditionSpec
4. 命中后执行对应动作列表
5. 若动作为动作块引用，则展开后执行

这说明：

- 规则循环并不需要自己重定义图像检测逻辑
- 它只需要“引用一个可复用的视觉判定条件”
- 线性脚本也一样

---

## 13. 为什么这样设计最合理

### 13.1 因为真正的复用不是“脚本模型复用”，而是“条件 / 动作对象复用”

如果片面追求“线性脚本和规则循环合并”，最终会产生：

- 相同意义的判断被重复复制
- 同一张图、同一块区域、同一阈值散落在各处
- 维护困难
- 规则脚本和线性脚本的语义被混在一起

### 13.2 统一视觉条件对象解决了根本问题

统一后的设计能够保证：

- 一张图只维护一份
- 一个区域只定义一次
- 一个阈值值只配置一次
- 线性脚本和规则脚本都引用同一个判定对象

这样才是真正的“复用”。

---

## 14. “无法加入”示例

假设有一个规则：

- 条件：识别到“无法加入”弹窗
- 动作：
  - 点击关闭
  - 等待 300ms
  - 点击重试

在新的设计下，系统会拆成：

> 以下为示意，非规范。字段以 [§11](#11-一个统一的数据模型) 为准。

### 14.1 视觉条件

取自现有 `RuleTemplates/LastCloudia/unable_to_join.rules.json` 的真实取值：

- Id = `LastCloudia.UnableToJoin`
- Name = "无法加入房间"
- TemplatePath = `LastCloudia/images/unable_to_join.png`
- RegionX1/Y1/X2/Y2 = 285 / 320 / 440 / 340
- MatchThreshold = 0.85
- MeanDiffThreshold = 30
- ReferenceOuterWidth / ReferenceOuterHeight = 750 / 1040

其中后两项是本轮新增（FR-10），取自该脚本的 `OuterWidth` / `OuterHeight`；其余字段迁移时原样搬过来。

### 14.2 动作片段

- Id = `LastCloudia.CloseAndRetry`
- Steps = [ Click(关闭), WaitTime(300ms), Click(重试) ]
- ConditionRefs = [ ]

### 14.3 规则

- Id = `LastCloudia.Rule.UnableToJoin`
- ConditionRef = `LastCloudia.UnableToJoin`（条件 **Id**，不是名称）
- Actions = [ ActionBlockRef(`LastCloudia.CloseAndRetry`) ]
- TriggerOnce = false

### 14.4 线性脚本也可以复用

线性脚本中也可能直接引用同一个条件，但带自己的调用方参数：

- WaitImage：conditionRef = `LastCloudia.UnableToJoin`，timeoutMs = 30000
- 然后：ActionBlockRef(`LastCloudia.CloseAndRetry`)

注意同一条件在规则循环里是单帧判定（无超时），在线性脚本里是轮询等待（有超时），条件对象本身不变——这正是 FR-09 的意义。

也就是说：

- 规则和线性脚本都依赖同一个视觉条件对象
- 动作也可以复用同一个动作块
- 但运行时语义仍然是线性或规则循环各自执行

## 15. 验收标准

### AC-01：视觉判定复用

给定同一张模板图片和同一块区域，规则脚本和线性脚本应共享同一个 VisualConditionSpec 实例或等价引用。

### AC-02：动作复用

给定同一动作片段，规则脚本和线性脚本都可在模板库中复用，并持久化为可导出结构。

### AC-03：运行语义不混淆

即使共享公共对象，规则循环仍然按“每帧判定 + 命中执行”执行，线性脚本依然按“顺序推进”执行。

### AC-04：模板分层

视觉条件模板、动作模板、线性脚本模板、规则模板必须各自归类，不能单一模板混用。

### AC-05：可序列化

所有核心对象必须支持 JSON 导入/导出，不依赖 UI 运行时状态。

### AC-06：迁移完整且等价

分两条，都必须满足：

**结构等价性（可自动化）**——现有 13 份 `.rules.json`（11 份 `RuleTemplates/LastCloudia/` + 2 份 `TestScripts/`）全部迁移为 `FormatVersion = 2`，且对每一份，迁移前后加载到内存后的下列内容逐项相等：

- 每条规则的判定内容：图片路径（解析为绝对路径后比较）、区域四元组、`MatchThreshold`、`MeanDiffThreshold`
- 每条规则的动作序列：类型、顺序、全部参数值
- 规则的相对顺序（即优先级）、`Enabled`、`TriggerOnce`
- 脚本级 `OuterWidth` / `OuterHeight`

**运行等价性（人工）**——至少覆盖 `unable_to_join`、`network_error`、`multi_game_refight` 三份，在真实游戏窗口下实跑，确认匹配命中与点击落点与迁移前一致。此项无法自动化（依赖游戏窗口在场），必须人工执行并记录结果。

另：`FormatVersion = 1` 的文件被加载时必须报错而非静默解析，错误信息含文件路径与版本号（FR-11）。

### AC-07：参照空间不匹配可被发现

当脚本 `OuterWidth/OuterHeight` 与所引用条件的 `ReferenceOuterWidth/Height` 不一致时，加载阶段必须产生明确的警告或错误，不允许静默按错误坐标执行匹配。

### AC-08：条件引用缺失有明确错误

`conditionRef` 指向不存在的 ID 时，错误信息必须包含脚本名、规则名（或步骤序号）和缺失的 ID。

### AC-09：超时不进入条件对象

同一个 `VisualConditionSpec` 可被两处 `WaitImage` 以不同 `timeoutMs` 引用，无需复制条件定义。

## 16. 设计上的关键结论

### 结论 1：线性脚本和规则循环不应该完全合并

原因：

- 一个是顺序执行
- 一个是持续监控
- 两者运行时语义不同

### 结论 2：动作复用和视觉条件复用必须统一抽象

因为它们分别对应：

- 可复用行为块
- 可复用判定块

### 结论 3：真正的高价值复用来自视觉判断对象

这比动作本身更重要，因为判断通常更稳定、更重复、更难维护。

### 结论 4：模板库应该分层

- 视觉条件模板库
- 动作模板库
- 线性脚本模板库
- 规则模板库

而不是单一模板库强行塞所有东西。

---

## 17. 对当前工程的落地建议

对于当前工程，推荐采取以下路线：

1. 保留现有线性脚本编辑器和规则循环编辑器的**功能**（线性脚本目前虽无实际脚本文件，功能必须保留）
2. 抽离公共"视觉判定模型"
3. 抽离公共"动作模板/宏动作模型"
4. 让两个解释器改为引用这些对象，并加上 `FormatVersion = 2` 版本闸门
5. **再做一次性迁移**：把 13 份内联条件脚本转为引用式，按 AC-06 验证等价
6. 迁移验证通过后，删除 `Rule` 上的内联条件字段与解释器中对应的旧求值分支

第 5 步必须在第 4 步**之后**：迁移工具的输出格式依赖新模型定稿，而验证迁移结果又依赖新解释器能实际跑起来。第 6 步必须在第 5 步之后，是收尾清理。执行顺序见 [Script_Reuse_Plan.md](Script_Reuse_Plan.md) §6。

各自解释器的**运行语义**保持不变（线性顺序执行 + 轮询等待，规则单帧首个命中），变的只是底层对象。

这样做的好处是：

- 既不破坏现有设计
- 又真正解决复用问题
- 能逐步演进，而不是一次性大改结构

---

## 18. 最终一句话总结

这套系统的正确设计不是“两个编辑器合并成一个”，而是：

- 共享底层判定和动作对象
- 保持线性脚本与规则循环各自的运行语义
- 让“视觉条件复用”和“动作复用”成为统一的底层能力

也就是说：

- “同一个脚本模型”不需要合并
- “同一套复用对象”应该统一

这是整个设计的核心。
